## 论点

vibecoding 消耗的不是 token，是**注意力**，而且是被动消耗：读解释、纠误解、追进度、记状态。
这些东西全在"对话层"，层次一低，人就只能一直在线。

所以 PAD 的终局不是"更好用的启动器"，而是**把人从对话层捞出来**：

> 过程归 PAD，人只出现在两个时刻：定标准、验收成果。

## 三层分离（防止 AI 自己验收自己）

| 层 | 谁产 | 规则 |
|---|---|---|
| **标准** ACCEPTANCE | 人写 / 人签字 | 任何 AI 起草的标准，必须经过人确认才算数 |
| **证据** EVIDENCE | 机器产 | 命令输出、退出码、commit、时间。不能是 AI 的复述 |
| **判定** | 机器算 | 断言跑过就是过；人保留否决权 |

这条不能省。松掉任意一层，"只验收成果"就退化成"盖橡皮章"。

## 人的三个时刻

1. **定标准**：写 ACCEPTANCE，一次性，之后很少改
2. **验收**：看一条结论 + 一条证据，点通过或不通过
3. **排优先级**：决定下一个 stage 是什么

除此之外，人不需要在线。不需要读它的解释，不需要回答"我理解得对吗"。

## PAD 的落点

- **实例 = 项目**。一个实例 = 一份隔离 `DSH_HOME` + 一个工作区 + 一个 profile
- **profile = 项目的工具预算**。不是"全局默认全量"，而是这个项目需要什么就装什么
- **验收台 = 唯一需要人的界面**。待验收队列里同时只放一件事
- **体检层 = 护栏**。因为人不在线，所以会话膨胀、工具膨胀必须在人看见之前亮灯

## 诚实的边界

"只验收成果"有个前提：**成果必须可判定**。

- 可判定：构建通过、测试全绿、diff 只有 X、接口返回 200
- 不可判定：这个 UI 好看吗、这段文案对吗、这个方向值得做吗

PAD 的作用是**把人的判断压缩到不可判定的那一小块**，不是消灭它。
凡是能用断言替代的判断，就不该占用人的注意力。

## P0：端到端最小闭环

一个 demo 项目，全程不出 PAD 窗口：

```
建瘦实例 → 写 ACCEPTANCE → pad cli accept → 证据落盘 → 卡片显示"待验收"
```

验收标准见根目录 `ACCEPTANCE.md`。
